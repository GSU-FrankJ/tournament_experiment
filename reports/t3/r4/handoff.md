# T3-R4 交接说明（给合作者）

本轮做了两件事：先把 `bwA`（`bw` 加上第 3 阶段的"验证器门限重启"）锁定为协议 T3-1.1；然后在全新的种子 80501–80540 上、q = 50 和 q = 60 各 40 个，共 80 个 run，按事先写好的规则做确认。结论先说：**确认通过：80 个 run 里 79 个通过，只有 1 个失败；规则要求失败不超过 6 个，并且每个 q 不超过 4 个。**独立重算的程序给出相同的结果。

## 1. 锁定了什么

- **协议 T3-1.1 = T3-1.0（锁定的 `bw`）加一个配置项** `stage3_retry = {"delta_gt": 0.005, "max_retries": 1}`。训练代码（`run/ms_retry.py`、`run/run_ms_stagewise.py`）与 T3-R3 完全相同：相对 T3-R3 的预登记提交，`agents envs utils run tools/ms tools/v2` 没有任何改动。
- **重启的行为**：在第 3 阶段本地更新 1600 处读开发层验证器的单步偏离增益 `Delta`；若 `Delta` > 0.005（或 `Delta`、`s`、`C` 不是有限数，或 `s` ≤ 0），就把第 3 阶段原地重新初始化一次并重训，冻结第二次的结果，第一次的产物移到 `attempt1/`，不覆盖、不删除；没有触发的 run 与 `bw` 逐位相同。触发的 run 预算是 5,400 次更新（没触发的是 3,800）。
- **锁与发射**：锁文件和 LOCK 记录（提交 `98355d8a` 与 `141b5189`）在发射之前就已推送。锁里记录了 33 个文件的 SHA-256。发射器启动时逐项检查：T3-1.1 的记录是 `protocols/LOCK` 的最后一条、锁文件与所有列出的文件的哈希一致、HEAD 就是 LOCK 记录所在的提交、工作树在 `results/` 之外干净、冻结的代码目录相对基准提交没有改动、根目录是绝对路径；任何一项不满足都拒绝启动。
- **规则（T3-R3 的预登记，在任何开发 run 之前就已写好）**：80 个 run 里至多 6 个失败，且每个 q 的 40 个里至多 4 个失败。若每个 run 独立地以概率 f 失败，规则被满足的概率在 f = 0.03、0.05、0.10、0.15 时分别是 0.982、0.865、0.271、0.030。

## 2. 确认结果

| q | run 数 | 通过 | 失败 | 失败上限 | 通过率的精确 95% 区间 |
|---|---|---|---|---|---|
| 50 | 40 | 40 | 0 | 4 | [0.912, 1.000] |
| 60 | 40 | 39 | 1 | 4 | [0.868, 0.999] |
| 合计 | 80 | 79 | 1 | 6 | [0.932, 1.000] |

- 80 个 run 全部正常结束，没有基础设施故障，没有任何 run 被重跑、替换或重抽；所有事后检查（退出码、文件完整性、清单中的提交与干净树、全局随机数断言、配置与计划一致、预算与学习率、导出、初始化摘要、冻结数组的逐位重放）在 80 个 run 上全部通过。
- **重启的触发**：80 个里触发 5 个（6.25%，精确区间 [0.021, 0.140]），全部在 q = 50（5/40），q = 60 为 0/40；5 个触发的 run 第二次尝试**全部通过**。把每个触发的 run 都记为第一次尝试失败，通过数是 74/80（0.925），这就是本批的"`bw` 等价"通过率；这 6 个第一次尝试失败里 5 个在 q = 50，所以在同一条规则下 q = 50 会超过上限 4（只是描述，不是检验）。事后独立复核把 5 个触发 run 的第一次尝试网络在最终验证层级（final tier）上重新评估：`eta_3` 都在 0.005 以上，每个都会通不过 G-A。
- **唯一的失败**是 q = 60、种子 80502（G-F 与 G-N）：第 2 阶段有一个 5 个节点的近零努力段（最长段在 d ∈ [-22, -14]；`Gmax_full` = 0.0586，上限 0.01，出现在 d = -14），该 run 处在第 3 阶段的夹紧区间里（S3 = 0.536），属 T3-R3 的 (K) 类。它的第 3 阶段指标全部通过（最后 16 次导出里 `rmse_pos` 有一次到 0.0505，终点是 0.0214），而第 3 阶段末的触发量 `Delta` 只有 0.0008（上限 0.005）——重启看不见这类失败。这是 T3-R3 开发批和本批共 120 个 `bwA` run 里的第二个同类失败（另一个是开发批 q = 60 的种子 70511），都在 q = 60。
- **成本**：没触发的 run 3,800 次更新，触发的 5,400 次（1.421 倍）；80 个 run 平均 3,900 次更新（**1.026 倍**）。实测墙钟平均每个 run 597.6 秒；触发的 run 平均 801 秒，没触发的 584 秒（多 37%）；整批 22.9 分钟（40 个并行进程），各 run 墙钟之和 47,810 秒。
- **描述性对比（不做检验）**：本批与 `bwA` 的 40 个开发 run 合并是 118/120（0.983，[0.941, 0.998]）；T3-1.0 的三批 `bw` 是 36/40、34/40、37/40，合并 107/120（0.892，[0.822, 0.941]）；第一次尝试口径下 T3-1.0 对应的通过率是 74/80。
- 通过的 79 个 run 里，离门限最近的是 `eta_3` = 0.004897（门限 0.005 的 98%，q = 60 种子 80528）和 `rmse_pos` = 0.0454（门限的 91%）；有 6 个 run 的 `eta_3` 超过门限的 80%。没触发的 run 里有 3 个离触发门限不到 5%（`Delta` = 0.004897、0.004825、0.004758），都通过。

## 3. 论文里该怎么写 A

- **原句**（英文，在锁文件 `protocols/v2_T3_locked_v1_1.md` 里一字不差）的意思是：这是一个"终端阶段的验证器门限重启"——当第 3 阶段末的开发层单步偏离增益超过门限 0.005 时，把第 3 阶段重新初始化并重训一次，保留第二次的结果；它的成本是方法成本的一部分。
- **要同时报告的数字**：触发率（确认批 5/80；开发批与确认批合计 7/120，全部在 q = 50）、成本（更新次数 1.026 倍；触发的 run 约 1.42 倍更新、约 1.37 倍墙钟）、确认结果（79/80，规则要求不超过 6 个失败，实际 1 个）、第一次尝试口径的通过率（74/80）以及 T3-1.0 三批 `bw` 的通过数，并说明规则和种子是在开发 run 与锁定之前就定好的。
- **要写明的局限**：重启针对的是在第 3 阶段检查里看得见的失败；本批没有对照臂，第二次尝试是一次新的抽样，所以"5 个触发的 run 第二次全部通过"本身并不能衡量重启之外"再抽一次"的效果；剩下的失败类型是 q = 60 的第 2 阶段近零段（开发批和确认批共 60 个 q = 60 的 `bwA` run 里有 2 个），重启够不到；重启是否以及如何起作用，没有被确立（第二次尝试可以仍在夹紧区间里并通过，也可能第一次不在区间里、第二次进入区间并通过）；这是一个 80 个 run 的批次。

## 4. 工具与检查

- 新工具 `tools/t3/t3r4_*`（发射器、锁生成器、事后检查、评估、分析、独立重算、C-REPRO、事后脚本）及 109 个新测试；两轮独立评审（没有阻断性问题，共 27 条意见，全部处理，见 `02_checks.md`）；锁之前在 80 个符号链接到 T3-R3 生产 run 的目录上做了一次预演（评估、检查、分析、独立重算、报告表格都跑通）。
- **C-REPRO**：把 T3-R3 的 `bwA` run（q = 50 种子 70508，触发过；q = 60 种子 70501，没触发）用各自的 `run_config.json` 在最终代码提交上重跑，与原始 run 逐位相同（162 个 npz 文件、第 2 与第 3 阶段末状态、各 JSON 记录、训练历史；触发的那个还包括 `attempt1/` 和 `retry.json`）。
- 全量测试 1,928 通过，6 跳过，2 个 xfail，2 个已知失败（`test_registry_canonicalization`；`test_the_existing_launcher_is_unchanged`，自 T3-1.0 锁定改动 `protocols/` 起就失败）。
- 报告由另一个只读的核查程序分两轮逐项核对过，没有发现错误的结果数字；更正涉及措辞、归属、一处测试用例数目（'八个'应为'六个'）、一处单位（把墙钟之和写成了 CPU 小时）和一处没有记录支持的负载数字，已全部处理，清单见 `pi_record/01_factcheck.md`。
