**Paper wording for A (verbatim):**

> a verifier-gated restart of the terminal stage: when the development-tier one-step deviation gain at the end of the stage-3 phase exceeds the gate's limit 0.005, stage 3 is re-initialised once and retrained, and the second attempt is kept; its cost is part of the method's cost.

## 2. Confirmation design

- q in [50, 60]; seeds 80501-80540 (the same 40 seeds at both q): 80 runs, arm `bwA` only; run names `t3r4_q{q}_s{seed}_bwA`; directories `results/t3_r4/confirmation/q{q}/seed{seed}/bwA`.
- Each config is T3-R1's `bw` config of the same q with `stage3_retry` added and only these fields set: `seed`, `run`, `record.run`, `record.seed`, `record.output_dir`, `pilot` (`pilot` = "t3_r4").
- Seed block: reserved in round T3-R3 and never trained (reports/t3/r3/04_preregistration.md section 12).

## 3. Gates (T3-R1's, inclusive `<=`, full float64 precision)

| Gate | Criterion |
|---|---|
| G-A | `eta_T_over_dw` <= 0.005, `rmse_pos_T_over_eT0` <= 0.05, `tail_mean_T_over_eT0` <= 0.02 (final tier) |
| G-F | `Gmax_full_over_dw` <= 0.01 (final tier) |
| G-N | development minus final: abs diff of `eta_T_over_dw` <= 0.001 and of `Gmax_full_over_dw` <= 0.001 |

**Run pass:** exit code 0; the process-global RNG assertion is ok; a valid evaluation (final and development tier); and G-A and G-F and G-N.

## 4. Confirmation rule

- the confirmation passes iff at most 6 of the 80 runs fail and at most 4 of the 40 runs fail at q = 50 and at most 4 of the 40 runs fail at q = 60; otherwise it fails.
- Rationale: fixed before any development run in the pre-registration of round T3-R3 (reports/t3/r3/04_preregistration.md section 9, D6) and binding here.
- Operating characteristic (independent per-run failure probability f, the same at both q): pass probability 0.9999 at f = 0.01, 0.9818 at f = 0.03, 0.8648 at f = 0.05, 0.2708 at f = 0.1, 0.0299 at f = 0.15.

## 5. Failure counting

- every planned run is reported; no seed is replaced or re-drawn.
- Infrastructure failure, only if one of these holds:
  - a negative return code (a signal, e.g. SIGKILL)
  - an out-of-memory kill recorded in the kernel log or the run's log
  - OSError ENOSPC recorded in the run's status.json or traceback
- Ledger: `results/t3_r4/confirmation/infra_events.json; the analysis tool and the blind tool both read it`.
- Re-run: the attempt is moved to results/t3_r4/confirmation/crashed/ and the run is repeated once into the original path; if the repeat also fails for an infrastructure reason the confirmation stops without a verdict (no pass or fail is declared).
- Other failures: any other nonzero exit, and any global-RNG violation, is a failed run.
- Evaluation problems: an evaluation error, or an evaluation with valid = False, counts as a failed run unless a re-run of the locked evaluator on the same weights succeeds; the re-run is reported; a completed run is never re-trained.
- The scheme's own steps: a re-initialisation of stage 3 inside a run (the retry of stage3_retry) is part of the run, never a re-run.

## 6. Reported, deciding nothing

- pass counts per q and in total with exact Clopper-Pearson 95 % intervals
- the worst Gmax_full and its run; the medians of eta_3, rmse_pos_T_over_eT0, tail_mean_T_over_eT0, peak_T_signed, Gmax_full and EXP_root
- the fire rate of the trigger with the runs, and the first-attempt outcome (the pass count with every fired run counted as a failure of its first attempt)
- per failing run: the failing gates and values, the stage of the failing quantity, S3, the stage-2 stretch, the last-16-export range of the failing stage-3 quantity, and its class (F), (K), (V), (E) or (U) as in T3-R3's D2
- cost: updates, policy rows and wall time per run, and the share of fired runs
- descriptive comparisons: this confirmation pooled with bwA's 40 development runs of T3-R3; the three blocks of bw (T3-R1, T3-R2, T3-R3 development); the pass rate of T3-1.0 implied by the first-attempt outcome

If the confirmation fails: nothing is changed or tried; the PI decides the next step.
