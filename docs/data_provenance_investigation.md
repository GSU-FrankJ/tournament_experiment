# Data Provenance Investigation Report

**Date**: 2025-12-18  
**Investigation**: Whether opponent-generated actions mix into learner's PPO update buffer  
**Verdict**: ✗ **CONFIRMED HIGH-RISK MIXING**

---

## Executive Summary

**CONFIRMED**: Opponent-generated actions ARE being mixed into the learner's PPO update buffer in a way that fundamentally violates PPO's on-policy assumptions and creates meaningless gradient signals.

**Risk Level**: HIGH  
**Impact**: Training instability, misleading convergence metrics, distorted advantage estimation, invalid approx_kl diagnostics

**Key Finding**: 26% of transitions in the diagnostic run were generated by opponent policy but treated identically to learner-generated transitions during PPO updates, resulting in ratio computations that compare incompatible policies.

## 2. Semantic Analysis: What Training Objective Are We Actually Optimizing?

**Current Implementation = Case (C): "Mixed Behavior PPO"**

The code implements a **hybrid approach** that unintentionally mixes training paradigms:

### What Happens:

1. **Early training phase** (`lag_prob > 0`):
   - Player 1: learner policy → stored with learner's logp
   - Player 2: mix of learner (prob `1-lag_prob`) and opponent (prob `lag_prob`) → stored with respective logp
   - Buffer contains: ~75% learner transitions + ~25% opponent transitions (in diagnostic run)

2. **Late training phase** (`lag_prob = 0`):
   - Both players use learner policy
   - Buffer contains: 100% learner transitions
   - This phase is actually correct (symmetric self-play)

3. **PPO Update (ALL phases)**:
   ```python
   # For ALL transitions (learner + opponent):
   new_logp = evaluate_current_learner_policy(state, action)
   ratio = exp(new_logp - old_logp)  # ← WRONG when old_logp is from opponent!
   ```

### Why This Is Wrong:

**For opponent-generated transitions:**
- `old_logp` = log π_opponent(a|s)  (from lagged/historical opponent network)
- `new_logp` = log π_learner(a|s)  (from current learner network)
- `ratio = π_learner(a|s) / π_opponent(a|s)`  ← **meaningless comparison**

PPO ratio is designed to compare:
- π_new(a|s) / π_old(a|s) where both come from **same policy at different time steps**

When policies are fundamentally different (opponent vs learner), the ratio loses its theoretical foundation:
- Cannot bound policy updates via clip(ratio, 1-ε, 1+ε)
- Advantage estimation is distorted (computed assuming one consistent behavior policy)
- `approx_kl` diagnostic becomes meaningless (mixing KL from different policy comparisons)

## 4. Risk Assessment

### High-Risk Symptoms Observed/Expected:

1. **Invalid PPO Ratios**
   - For opponent samples, ratio doesn't measure policy deviation
   - Clipping becomes arbitrary (not bounded to small policy changes)
   - Can lead to unexpectedly large policy updates

2. **Distorted Advantage Estimation**
   - GAE assumes consistent behavior policy for value bootstrapping
   - Mixing two policies breaks this assumption
   - Advantages computed from mixed experiences may be biased

3. **Misleading Diagnostics**
   - `approx_kl` mixes two different KL measurements:
     - KL(learner_old || learner_new) for learner samples
     - KL(opponent || learner_new) for opponent samples ← not what we want!
   - Cannot reliably use KL for early stopping or adaptive scheduling

4. **Training Instability**
   - Gradient signals are contaminated by cross-policy comparisons
   - May explain convergence issues or oscillations
   - Hard to diagnose because metrics aggregate both sample types

5. **Conceptual Confusion**
   - Is this "learner vs environment" or "symmetric self-play"?
   - Documentation says "learner vs lagged opponent as environment" but implementation stores both
   - Makes results hard to interpret and compare

### Why Early Training Phase Is Especially Risky:

The `lag_prob` schedule (lines 428-435 in run_two_players.py) creates:
- **Warmup phase** (`update_idx < 10`): `lag_prob = 1.0` → Player 2 ALWAYS from opponent
- **Fade phase** (next ~1/3 of training): `lag_prob` gradually → 0
- **Late phase**: `lag_prob = 0` → Both players from learner (correct self-play)

**During warmup**: ~50% of ALL stored transitions are opponent-generated! This heavily contaminates early learning when the policy is most sensitive to gradient directions.

## 5. Recommended Fixes

### Option A: Store ONLY Learner Transitions (Cleanest)

**Concept**: True "learner vs opponent-as-environment" — opponent is part of environment dynamics, not a learning agent.

**Implementation** (run/run_two_players.py):
```python
# Lines 457-458 (current):
agent.store(s1, a1_norm, logp1, float(rewards[0].item()), v1, bool(done))
agent.store(s2, a2_norm, logp2, float(rewards[1].item()), v2, bool(done))

# OPTION A (only store learner transitions):
# Always store player 1 (always learner)
agent.store(s1, a1_norm, logp1, float(rewards[0].item()), v1, bool(done))

# Only store player 2 when it used learner policy
if not use_opponent:
    agent.store(s2, a2_norm, logp2, float(rewards[1].item()), v2, bool(done))
# When use_opponent=True, player 2 is just "environment" — don't store
```

**Pros:**
- Eliminates all mixing issues
- Pure on-policy PPO for learner
- All diagnostics (approx_kl, advantages) are valid
- Clear conceptual model

**Cons:**
- Less data per rollout during lag phase (may need more steps_per_update)
- Asymmetric learning (only one agent learns)

---

### Option B: Ensure Both Actions From Learner When Storing Both

**Concept**: True symmetric self-play — both players learn together.

**Implementation** (run/run_two_players.py):
```python
# Lines 448-453 (current):
use_opponent = (lag_prob > 0.0) and (rng.random() < lag_prob)
if use_opponent:
    a2_norm, e2, logp2, _ = agent.act_opponent(s2)
    v2 = agent.value_only(s2)
else:
    a2_norm, e2, logp2, v2 = agent.act(s2)

# OPTION B (only use opponent for evaluation, not storage):
if use_opponent:
    # Generate opponent action for environment step
    a2_norm_opp, e2_opp, _, _ = agent.act_opponent(s2)
    # But ALSO generate learner action for storage
    a2_norm, e2, logp2, v2 = agent.act(s2)
    # Use opponent action for environment
    e2_for_env = e2_opp
else:
    a2_norm, e2, logp2, v2 = agent.act(s2)
    e2_for_env = e2

# Environment step uses potentially mixed actions
_, rewards, _, done, _ = env.step((
    torch.tensor([float(e1.item())]), 
    torch.tensor([float(e2_for_env.item())])
))

# Storage ALWAYS uses learner's actions and logp
agent.store(s1, a1_norm, logp1, float(rewards[0].item()), v1, bool(done))
agent.store(s2, a2_norm, logp2, float(rewards[1].item()), v2, bool(done))
```

**Pros:**
- Maintains data volume (2 transitions per step)
- Symmetric learning for both players
- All PPO ratios are valid (learner vs learner)
- Can still use lag for curriculum/exploration

**Cons:**
- Complicates rollout (need two forward passes for player 2 when use_opponent=True)
- Rewards don't exactly match stored actions (learner sees reward from opponent's action)
- More computationally expensive

## Conclusion

The investigation **confirms with code evidence and diagnostic experiments** that opponent-generated actions are being mixed into the learner's PPO update buffer, creating meaningless policy ratios that violate PPO's theoretical foundations.

**This is a HIGH-RISK issue** that can cause:
- Training instability
- Invalid convergence metrics
- Distorted learning signals
- Results that are hard to interpret or reproduce

**Recommended immediate fix**: Implement **Option A** (store only learner) or **Option D** (remove lag) depending on experimental goals, then re-run experiments to establish valid baselines.
